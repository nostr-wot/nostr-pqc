# Audit: complexity, payload sizes and interoperability

Reviewed 2026-09-11. Scope: drafts 01-06, the existing SDK envelope/DM composition, and the proposed public-event proof. This is an engineering review, not an independent cryptographic audit or an interoperability certification.

## Assessment

The confidentiality-first migration is a practical incremental design for upgraded peers: it preserves the relay event model and concentrates new cryptography in the signer. Keep the existing two-byte envelope header. A universal event selector would add overhead without helping opaque relays decrypt anything.

The relay discovery proposal is relatively small. Public hybrid authentication is substantially harder: its signature format is only part of the work. Persistent trusted-key state, historical attestation availability, rotation, downgrade prevention and event-reference semantics must be resolved before deployment. Keep draft 06 experimental; do not advertise it as ready merely because a relay can verify ML-DSA.

## Reproducible size model

Run `node scripts/nip-payload-sizes.mjs` from the repository root. The committed [JSON results](payload-sizes.json) are generated by that script. Values are uncompressed UTF-8 bytes in a client `EVENT` message, using ASCII content, one recipient tag, ten-digit timestamps and the existing seal-layer hybrid placement. Ciphertext and signature placeholders have exact serialized lengths. There are no live keys or network sends.

For a serialized rumor of `n` bytes below 65536 and padded body length `P(n)`, classical encryption occupies `P(n) + 67` binary bytes, and the local hybrid envelope occupies `P(n) + 1612`. The binary difference is 1545 bytes, not 1568: nonce and authentication-tag sizes differ too. Each layer is base64-encoded, with length `4 * ceil(bytes / 3)`, and the outer encryption pads the JSON seal again. Consequently the final difference is not constant.

|---|---:|---:|---:|---:|
| 1 | 1711 | 4615 | 2904 | 2.70 |
| 32 | 1711 | 4615 | 2904 | 2.70 |
| 280 | 2567 | 5295 | 2728 | 2.06 |
| 1024 | 3931 | 7343 | 3412 | 1.87 |
| 4096 | 11439 | 14171 | 2732 | 1.24 |
| 16384 | 38747 | 44207 | 5460 | 1.14 |
| 32000 | 66055 | 66055 | 0 | 1.00 |

The equal 32000-byte row is real padding-bucket behavior: both seals fit the same outer padded length. It does not eliminate the hybrid cryptographic work or its inner size overhead. Multibyte text, escaping, additional tags, recipient lists and timestamp widths change the results. WebSocket framing, TLS, subscriptions, acknowledgments, relay replication and downloaded attestations are excluded.

Cross-check performed: all seven rows in both modes matched actual encryption output lengths using the local `@nostr-wot/pq` build and `nostr-tools@2.24.1`; all 14 inner encryption/decryption round-trips recovered their inputs. Keys were generated for the check and no events were published. This checks the size model against the shared implementation, not independent client interoperability or full DM signature validation.

### Public proofs and key discovery

The draft-06 proof contains 4628 binary bytes, including its selector, or 6172 base64 characters. Including tag framing, profile name and attestation reference adds **6275 bytes** to an otherwise tagless event. The model's 280-byte public note grows from **632 to 6907 bytes**, about **10.9 times** its original size. One million such events add approximately **6.275 GB** per stored replica before database overhead or compression. Even a like/reaction pays this proof cost if opted in.

The draft-02 derived-key attestation is **12210 bytes** in the modeled `EVENT` message. Its large public keys are downloaded and cached per identity/key version, rather than repeated in draft-06 events. Cold-cache relay validation can nevertheless cause a dependency-fetch amplification attack. Cap requests, deduplicate in-flight lookups, bound cache growth and reject unresolved dependencies without claiming successful validation.

### Groups and replication

NIP-17 requires separate recipient copies, plus a sender copy if recoverability is wanted. Ten total copies of the modeled 280-byte hybrid message cost **52950 bytes** before relay replication; at three relays per copy that is **158850 bytes** of publish payload. The corresponding classical totals are 25670 and 77010 bytes. Larger recipient tag lists increase the underlying rumor too, so these totals are illustrative lower estimates, not exact ten-person room measurements.

Do not union fallback relays into recipient inbox lists to solve a size rejection. Do not reuse one KEM encapsulation across recipients as an optimization. A session/group key design could amortize costs, but would introduce a different protocol with membership, rotation and compromise-recovery requirements.

### Length ceilings

Draft 03's limit is 65535 bytes of serialized rumor. It is not a 65535-character chat limit. A client with the older 65535-byte outer NIP-44 plaintext ceiling also needs the serialized seal to fit that ceiling: in this particular fixture the largest chat text is **40682 bytes** in both modes. The next padding bucket exceeds the ceiling. Different tags change that boundary.

Current upstream NIP-44 specifies an extended prefix for larger plaintexts; the local PQ profile does not adopt it automatically. Large-message interoperability requires explicit library-version/resource-limit checks. A relay's message-byte and content-character limits are additional, independent constraints. Do not raise defaults to the protocol maximum: parsing/base64/decryption can hold multiple copies in memory.

## Complexity and interoperability matrix

| Component | Added work/state | Legacy behavior | Assessment |
|---|---|---|---|
| Two-byte envelope selector | Constant-time dispatch on public bytes; no added ordinary-event bytes | Legacy decryptor rejects the private format | Keep existing framing and fail closed |
| Hybrid confidentiality | One ML-KEM encapsulation/decapsulation per copy, KDF and AEAD, recipient attestation lookup | Ordinary relays can carry it within policy; old recipients cannot decrypt | Viable for explicitly capable peers |
| NIP-07 capability options | Signer discovery plus account-specific rejection handling | Old signers may ignore surplus arguments | Verify advertised capability and returned envelope; no silent fallback |
| Custom derivation selectors | Exact path/selector recovery metadata and matching KDF inputs | Numeric-selector SDK API does not imply custom-path support | Publish cross-language path vectors before claiming interoperability |
| NIP-11 crypto namespace | Small document parser and truthful verifier-policy configuration | Old clients ignore the extension | Advisory discovery; no trust or downgrade authority |
| Public ML-DSA proof | BIP-340 plus ML-DSA verification, key resolution, persistent pins, replay identity | Old clients see content but cannot enforce PQ authentication | High complexity; deployment blocked on remaining protocol work |
| Private sender authentication | New private proof design, identity binding and deniability analysis | Current seal remains classically authenticated | Outside current proposal; never expose sender proof on public wrapper |

Cost per message grows with recipients and relays, not with selector width. Verification throughput and mobile signing latency were not benchmarked here. Measure p50/p95 latency, allocations, cold/warm attestation cache behavior and rejection floods before setting relay budgets. Key derivation timing is device-dependent; it is not a guaranteed few-millisecond operation.

## Findings and corrections

1. **High: legacy transport is not end-to-end compatibility.** Preserve this distinction throughout. Draft 03 substitutes encryption inside the seal; it does not make a legacy NIP-17 recipient PQ-capable. Group sends need a capability policy for every copy.
2. **High: signature stripping and mutable event IDs remain deployment blockers.** A forged classical key can strip a proof or re-sign an already PQ-authenticated logical transcript. Draft 06 identifies pins and logical replay keys, but replies/deletions/reference aliases and authenticated rotation still need complete specifications. Restrict the proposal to review until those are resolved.
3. **Medium: draft-02 possession wording was too strong.** An ML-DSA signature binds the KEM public key; it does not prove possession of the KEM secret. Corrected without changing bytes.
4. **Medium: size and security claims were overbroad.** Replaced the constant outer-overhead claim with this reproducible model. The hybrid does not become literally NIP-44 if its KEM fails, because the AEAD and combiner differ. Whole-call JavaScript timing uniformity is not established by generic error messages.
5. **Medium: current NIP-44 and this profile have different length support.** Clarified the short-message limit and nested encoding ceilings. NIP-44 also marks version 1 deprecated/undefined; the local `0x01 0x01` pair is not an official allocation. An independent reader must explicitly opt into this envelope namespace.
6. **Medium: independent interoperability remains unverified.** Obelisk and the extension using the same SDK are integration evidence, not two independent implementations. Require derivation, attestation, envelope, unsupported-suite and negative verification vectors across implementations. Other PQ Nostr formats are not compatible solely because they use ML-KEM.
7. **Low: move-related link and formatting issues.** Fixed the broken draft-index table boundary and stale implementation-relative paths. Preserved every prior document filename as a pointer in the extension. Old file URLs work as landing pages; old heading fragments and raw-content consumers cannot automatically redirect to another Git repository and should update to the canonical URL.

## Recommended sequence

Keep the confidentiality envelope and explicit signer negotiation. Add conformance vectors and bounded size preflight in implementations as separate reviewed changes. Implement optional relay discovery only alongside a real verifier and documented policy. Complete key lifecycle/reference semantics and obtain independent review before deploying public hybrid authentication. Consider alternative standardized parameter sets only as newly specified suites with an explicit threat-model tradeoff; reducing a key size is not a transparent optimization of the current suite.
